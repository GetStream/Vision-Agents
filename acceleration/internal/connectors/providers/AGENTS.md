# internal/connectors/providers

The built-in connector manifests: one `<id>.yaml` per connector, in the schema `core.ParseManifest` reads (`internal/connectors/core/manifest.go`). `providers.go` embeds them; at every start the router's `openStore` calls `store.SeedConnectorDefinitions` (`internal/store/connectors.go`), which writes each one to `connector_definitions` under the built-in customer.

## Rules

- **One YAML per built-in, and the id is the file name.** `slack.yaml` holds `id: slack`. The seeder refuses a file whose id is not its name.
- **No built-in id starts with `custom_`.** That prefix belongs to custom definitions, so a customer's definition can never shadow a built-in. The seeder and a CHECK on the table both refuse it.
- **Any change to what a manifest says gets a new `revision`**, as a migration gets a new number. The seeder stores each file at the revision it names, because builds with different files share a database: old and new pods in a rolling deploy, a rollback, a branch build beside an accelerate build on staging. A build that finds its own revision stored changes nothing, and an older build never makes its revision latest again.
- **An edit without a new revision stops the router from starting**, with the file and revision named, so a connection pinned to a revision never reads two manifests. "Changed" means the parsed manifest changed, not the file: the seeder compares the JSON `core.Manifest` marshals to, so comments, spacing, key order and quoting need no new revision. A change to `core.Manifest` that moves those JSON bytes for a stored built-in does the same to every router at once; `TestTheBaseBuiltInsMarshalAsTheyWereStored` (`internal/store`, goldens in `internal/store/testdata/builtins`) pins them.
- **Reverting a manifest is a new revision** whose content is the old one. Rolling the router back does not make an older manifest latest.
- **A revision that never worked is marked broken by a later one**, with why: `broken_revisions: [{revisions: [1, 2, 3, 4], reason: "..."}]` in the new revision's file (`slack.yaml`, revision 6). Marking is a change, so it is a new revision. The seeder stores the marks in `connector_broken_revisions`, and they only accumulate: a later revision that drops the list, or gives another reason, unmarks nothing, and a mark keeps its first reason. A connection on a marked revision is refused a credential, so its person logs in again, and that consent pins the latest revision. The API shows it as `definition_status: broken` with `definition_broken_reason`. Only a revision before the file's own can be marked. Check: `go test -tags integration -run 'TestStoreSuite/(TestSlackRevisionSix|TestSeedingABuiltInStores|TestAMarkStays|TestAConnectionsDefinition)' ./internal/store`.
- **Removing a file removes nothing.** Its revisions stay in the table for the connections that pinned them.
- **An invalid manifest stops the router from starting**, with the file and the field named. The unit tests in `internal/store` parse every file here, so `go test ./internal/store` catches one before a deploy does.
- **Every vendor fact carries its source** in a comment beside it: a vendor page (with the date it was opened), a line of the prototype `internal/mcp/connectors.yaml` on `codex/connector-support` at `cf62af0d`, a row of the architecture doc (`acceleration/docs/connectors/architecture.md` on `connectors/planning`), or a fixture in `internal/connectors/core/testdata/manifests/`. A value with no source is marked `# unverified` and listed in the PR.
- **`internal: true` hides a built-in from every app but Stream's own**: the lists, lookups, connections and OAuth clients of an app whose `apps.settings.internal_connectors` is `true` see it, any other app and any customer with no app row does not. It holds per revision: a public built-in made internal later keeps its earlier public revisions visible. Check: `go test -tags integration -run 'TestStoreSuite/.*(Internal|Flag)' ./internal/store`.
- **`owner_email: true` makes a user-owned connection's first consent sign in as its owner** (`nessy.yaml` revision 4, AI-1543): the `email` captured from the `id_token` must be the one the app's backend last sent for that user in `X-Stream-User-Email`, compared without case; otherwise the consent ends `account_mismatch` and nothing is stored. It needs a required `email` capture from the `id_token`, so the scheme checks the token's `iss`, `aud` and `exp`; an `email_verified` capture, which refuses the consent when not `true`, must come from the `id_token` too, never the browser's `callback_query`. Check: `go test -tags integration -run 'TestAuthorizationsSuite/(TestAnOwners|TestAnotherPerson|TestAConsentIsRefusedWhen|TestAChatConsentIsChecked)' ./internal/api`, and `go test -run 'TestManifestSuite/TestOwnerEmail' ./internal/connectors/core`.
- **`sensitive: true` keeps outbound tools away from a connector that reads private data** (AI-1545, `nessy.yaml` revision 2). A config that binds one is refused with a 400 naming each tool that sends data out: a binding whose connector has a source that does not say `outbound: false`, a binding with `sandbox` set, an MCP server, a plugin not on its read-only endpoint, and a sandbox that reaches the network (`sensitiveBindingsComplaint`, `internal/api/configs.go`). The deprecated plugin paths that name a plugin on a config run it too: a client set with `user` and the app's login of a catalog plugin (`internal/api/plugins.go`). `sources[].outbound: false` says the server offers only tools that read, with a vendor source beside it; `sources[].read_only_tools` names the tools that only read on a server that also offers tools that write (`bigquery.yaml`, `google_docs.yaml`, `google_drive.yaml`), and a binding granting only those by name is not outbound; `tool_patterns` stay outbound. Left out, a tool may write, so it sends data out. Tools a caller declares at createSession are the caller's and are not checked (AI-1642): one that sends data on to others should carry `approval`. Check: `go test -tags integration -run 'TestConfigsSuite/(TestNessy|TestAConfigWithoutASensitive|TestAnUpdateOrAPatch|TestAnUpdateKeepingABindingToAForceDeleted)|TestSyncSuite/TestASyncedNessy|TestPluginsSuite/(TestAClient.*Nessy|TestAnAppLogin|TestLoginsBesideNessy)' ./internal/api`.
- **Every id here is a provider name the core may not spell.** `TestCoreNamesNoProvider` (`internal/connectors/core/guard_test.go`) reads the ids from this directory into its deny list.
- **No Go here beyond the embed and its tests** for now. A provider's hook (`hooks:` in a manifest) is the only Go a provider may need, and it is added with the hook registry, not before.
- **Every plugin of `internal/plugins/plugins.yaml` has a built-in of the same id** (T58), which its logins move onto (`internal/pluginmigrate`), with the plugin's endpoint, scopes, client env and setup steps (`setup:`). The four Google ones share one client env, `GOOGLE`, which `bigquery` (no plugin) reads too. Check: `go test ./internal/pluginmigrate`.
- **A `sandbox` block lists only hosts that take the credential in a header** (`core.SandboxRule`, `github.yaml` revisions 6 and 7): code in a session's sandbox gets a placeholder in `sandbox.env`, which the sandbox's egress replaces only in a request header and only for `sandbox.hosts` (https://www.daytona.io/docs/en/secrets.md). Both brokers also replace it as Basic auth's password, which is how git sends it (the proxy broker by its rewrite; Daytona, shown live only for `git ls-remote` with the user name `x-access-token`, staging E2E 2026-10-22, session `01a16514-923c-7843-9214-40a94453f194`, against its docs; clone, push, private repos and other user names under Daytona are `unverified`). A host that takes the credential only as Basic, such as github.com for git (revision 7), is listed, and its comment says so. Each host carries its vendor page. A connection pinned to an earlier revision gets no block until it is reconnected. Check: `go test -run 'TestSandboxSuite' ./internal/connectors/providers`.
- **Every OAuth built-in has a consent test**, Slack's authorize URL and Linear's in `internal/connectors/schemes/oauth2code/oauth2code_test.go` and the rest, Slack's consent included, in `consent_test.go` here: Begin, the browser and Complete of `oauth2_code` against `internal/connectors/fakeprovider`, with each endpoint role the manifest writes pointed at the fake and none added, so the test takes the manifest's own discovery path, `client.registration`, scopes and capture rules. A behaviour no fake personality has is asserted as the failure it causes (Salesforce's identity URL), not faked here: new fake behaviour belongs in `fakeprovider`.

## Tests

From `acceleration/`: `go test ./internal/store ./internal/connectors/...` without Postgres (the store's unit tests parse every file here; `TestConsentSuite` here runs each consent), and with it:

```bash
ROUTER_POSTGRES_DSN='postgres://postgres:postgres@localhost:55432/model_router_test?sslmode=disable' \
  go test -tags integration -run 'TestStoreSuite|TestOpenStoreSuite' ./internal/store ./cmd/router
```

`github` also takes a personal access token by `bearer` (revision 3, AI-990). A live check against GitHub, with the token from the environment only and never printed; it skips without one, and CI sets none:

```bash
E2E_GITHUB_PAT=... go test -tags integration -run TestGitHubLiveSuite ./internal/connectors/providers
```
